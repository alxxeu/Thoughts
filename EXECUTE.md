# Execute — протокол работы над задачами

Этот файл описывает, как мы берём задачи в работу. Используется вместе с
[`BACKLOG.md`](./BACKLOG.md). Перед тем как приступить к любой задаче,
пришедшей от пользователя, сверяемся с этим протоколом.

## Правило 1 — сначала сверка с бэклогом

Когда приходит задача:

1. Проверяем `BACKLOG.md` — описана ли она там уже.
2. **Уже в бэклоге, план согласован** → следуем этому плану, не
   перепланируя заново.
3. **Не в бэклоге** → сначала план, потом код:
   - предлагаем план (через Plan Mode, если задача не тривиальна);
   - пользователь вносит правки;
   - пользователь одобряет план;
   - только после одобрения план фиксируется в `BACKLOG.md` (раздел
     "В работе"), и мы приступаем к реализации.

Не начинаем писать код по задаче, для которой нет одобренного плана в
`BACKLOG.md`, кроме тривиальных однострочных правок и явных опечаток —
для них план избыточен.

## Правило 2 — новые задачи и идеи не реализуются с ходу

Когда пользователь присылает в чате новую задачу или идею — она не
реализуется немедленно. Она сначала записывается в `BACKLOG.md`
(раздел "Backlog / Идеи"), и только затем для неё строится план
(см. Правило 1). Это разделяет "запомнить идею" и "начать её делать".

## Правило 3 — коммит только после обновления бэклога

Перед каждым `git commit`:

1. Открыть `BACKLOG.md`.
2. Обновить статус:
   - задача выполнена полностью → перенести в раздел "Готово";
   - выполнена частично → оставить в "В работе", завести отдельный
     пункт/подзадачу на оставшееся.
3. Только после этого — коммитить.

## Правило 4 — новый шорткат сразу идёт в список Shortcuts

Если задача добавляет клавиатурный шорткат новой функции — этот шорткат
в рамках той же задачи добавляется в справочный список в Settings →
Shortcuts, а не отдельным пунктом "потом". Список только для просмотра —
сами комбинации фиксированы, не переназначаются.

## Правило 5 — гигиена файла плана

Файл плана (`.claude/plans/...`) — рабочий черновик текущей задачи, а не
архив. Суть одобренного плана и так фиксируется в `BACKLOG.md` и в
git-истории коммита, так что держать её дважды незачем.

- Задача закрыта **полностью** (коммит, перенос в `BACKLOG.md` →
  "Готово") → её план целиком вычищается из файла плана.
- Задача закрыта **частично** → из плана не убирается, но у уже
  реализованных подпунктов дописывается "— Реализовано."

## Правило 6 — Figma: файл — источник истины

- Изменения в Figma — только шагами плагина `figma-plugin/` («Thoughts
  Builder»): `./build.sh <шаг>`, лог-сервер `python3 -I logserver.py`,
  запуск — hot reload или Plugins → Development → Thoughts Builder.
- Перед правкой — дамп текущего состояния (`01-dump`): автор правит файл
  руками, наши шаги не должны затирать его правки.
- Свои слои шаги помечают (`mark`, pluginData `thoughts`); повторный запуск
  обновляет только помеченное и не плодит копий.
- Результат проверяется PNG-экспортом (`snap` → `figma-plugin/logs/`), а
  не логом.
- Слои, которые автор доработал руками, не трогаем без явной просьбы.

## Правило 7 — сначала системные инструменты, потом своё

Перед работой над любой функцией — новой, исправлением ошибки или доработкой
старой — сначала изучаем, что уже даёт платформа:

- Подробно проверить, можно ли решить задачу готовым в iOS/macOS: SwiftUI,
  UIKit/AppKit, TextKit, системные модификаторы и API (документация Apple,
  WWDC, форумы разработчиков).
- Посмотреть, как это сделано в системных приложениях (Заметки, Сообщения,
  Почта, Напоминания, Файлы) и в известных открытых проектах — есть ли там
  такая механика и на чём она построена.
- Своё решение — только если системного нет или оно точно не подходит; в
  плане коротко записать, что проверили и почему не подошло.
- Если своё уже написано, а системное нашлось позже — предлагаем перейти на
  системное.

## Правило 8 — Space 1 в Debug неприкосновенен

Space 1 в Debug-сборках (Mac и iPhone) — личный Space автора для настоящих
заметок и идей. Его карточки и сам Space не читаем без нужды, не меняем, не
удаляем, не очищаем, не пересоздаём и не подменяем фикстурой. Скрипты и
подмена `board.json` обходят слот 1. Для тестов, правок и экспериментов —
Spaces 2–9.

## Цикл работы

```
Делаем → обновляем статус в BACKLOG.md → коммитим → следующая задача
```
